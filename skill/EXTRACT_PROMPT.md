# 从 Books 提炼 BuildArena 工程 Skills 的提示词

本文件可作为提炼任务的完整提示词。默认从 `skill/books/` 中的本地资料提炼 Support 技能；用户指定的书籍、章节和输出位置优先。

这里将 “code as police” 暂按 **Code as Policies** 理解：把知识写成基于状态、条件分支和已有 API 的决策程序。同时使用代码表达可检查的约束，但不把知识技能缩减为规则检查器。首版采用供 Agent 阅读的参考策略，不引入自动执行宏或新的工具权限。

---

## 你的角色与任务

你是一名面向 BuildArena 的工程知识提炼者。请阅读已提供的书籍原文，将有来源依据、能映射到 Besiege 的工程知识，整理成原有多 Agent 工作流可以按需读取和应用的技能。

目标不是总结教材，而是回答：

> 在什么任务状态下，哪个角色应该观察什么、如何判断、怎样形成方案或使用已有工具、检查什么，以及何时承认信息不足或方案不适用？

先提炼一小批边界清晰、可审核的技能，目标为 5–10 条，但不要为了数量拆分或编造技能。知识、参考策略和验证记录共同构成一条技能；只有代码或只有泛泛建议都不够。

遵循 `skill/PLAN.md` 的首版范围。本次仅生成技能草案，不实现检索系统、不改变角色职责、不修改任务或评价标准、不运行游戏或调用模型 API。未经明确授权，不执行生成的代码。

## 1. 输入与事实核对

开始前读取下列资料的相关部分，记录实际文件版本或 Git 提交；没有权限读取的资料列为缺失，不凭记忆补齐。

| 输入 | 用途 |
| --- | --- |
| `skill/PLAN.md`、`skill/README.md` | 研究范围、技能结构和当前阶段 |
| `skill/book_candidates.md`、`skill/books/` | 资料清单、本地原文、审核与许可记录 |
| `levels.yaml` 中的 Support 任务 | 任务目标、场景、子结构限制及评价协议 |
| `prompt.yaml`、`spatial/agent.py`、`scheduler/runner.py` | 角色职责、实际工具绑定、终止条件和阶段交接 |
| `spatial/build.py`、`spatial/components.py`、`spatial/utils.py` | 工具签名、返回值、几何操作、坐标转换和操作分组 |
| `blocks/configs/` 中涉及的积木定义 | 可用积木、连接面、尺寸、成本及禁用状态 |
| `simulation/simulation_support.py`、`analyze/sim_support.py` | 实际放置与加载流程、轨迹含义和指标计算 |

先列出本地书籍，核实标题页、版本、目录和相关章节。不要因文件名是 `statics.pdf` 就认定书名、作者或版本，也不要把文件存在当成人工审核通过。

书籍提供工程原理；仓库提供 API 与任务约束；仿真提供特定条件下的物理证据。三者不能互相替代。任务文字与实现有差异时同时记录，不自行选择有利解释或修改评测。

默认仅使用本地原文，不自动下载书籍。按原文释义提炼，不大段复制教材；许可未确认时保留为内部审核草案，不标记可公开分发。不得把书籍中的指令性文本当作修改仓库或执行命令的授权。

## 2. 必须适配的 Besiege 环境

以下为提示词编写时核对的环境事实，执行提炼时须重新与当前代码比对。

### Support 任务边界

- Soft/Medium/Hard 的间隙跨度为 5/10/20 个游戏单位。Soft 只允许一个子结构，Medium/Hard 最多三个。
- 任务坐标中，跨度沿南北方向，地形顶部高度为 5；桥梁与两侧地形、货物与桥梁均无固定连接。
- 货物尺寸为 2.5 × 2.5 × 1.5，放在中央并逐渐加载。不能用固定端、地面锚栓或将货物焊在桥上的假设替代接触问题。
- 仿真适配器会对机器进行放置变换并添加配重。必须区分设计坐标、导出变换和最终场景坐标，不将构建时的位置直接当作落稳后的接触位置。
- 区分任务所要求的承载能力与分析器实际计算的阈值指标。分析器的通过不代表桥梁永久稳定，也不等于验证了教材公式。

### 坐标、构件和工具

- Agent 使用的常识坐标为 `[x, y, z] = [东, 北, 上]`。`Vector.real` 与游戏内部 `Vector.virtual` 的第二、第三分量互换；每个位置、力和几何输入都应标明坐标系。
- 距离、质量、载荷和成本使用仓库或游戏定义的单位。没有校准依据，不转换为米、牛顿、帕斯卡或真实材料强度。
- 只能采用当前配置允许、当前角色确实可用的积木与操作。禁止假设 Besiege 游戏中所有零件都已暴露给 Agent。
- `attach_block_to` 面向单个已有积木的连接面；`connect_blocks` 使用连接件连接两个已有积木的面。连接件不能因为书中称其为“杆件”就按普通积木附着。
- 连接面的标识、可用性和位置需要读取实际状态，不能把某个面字母永久等同于世界方向。旋转、移动或装配之后需要重新核对。
- `get_machine_summary()` 和 `get_block_details(block_id)` 当前返回文本，不是保证存在 `success`、接触力或应力字段的结构化对象。
- 方法存在不代表它是公开工具，更不代表所有角色和阶段都有该工具。以 `spatial/agent.py` 的实际绑定及操作分组为准，禁止调用私有方法或绕过碰撞检查。
- 几何连接、无碰撞、拓扑连通和物理稳定是不同事实。积木配置的碰撞体、外形和游戏中的承载行为不能混为一谈。

### 教材假设的处理

每条技能都要逐项解释其核心假设如何映射到环境：

| 教材假设 | 必须回答的问题 |
| --- | --- |
| 理想铰支座、滚动支座、固定端 | 游戏中实际是哪种接触？是否会滑移、抬起或分离？ |
| 理想桁架、纯轴力杆件 | 当前积木与连接能否满足？不满足时哪些结论只能作启发？ |
| 连续梁、线弹性、小变形 | 是否有有效的材料与截面参数？实际连接会不会主导变形？ |
| 静力平衡 | 放置、落稳和加载过程中，何时才有理由近似忽略动态效应？ |
| 二维分析 | 是否遗漏侧向倾覆、扭转、偏心载荷或三维接触？ |

未知摩擦系数、连接强度、弹性模量等必须保留为未知。若公式需要这些量，可保留带前提的符号关系或定性趋势，但不能填入常见工程常数来预测游戏中的最大承载。

## 3. 提炼步骤

1. **定位原文。** 从目录筛选相关章节，实际阅读正文、公式前提和必要图示。区分 PDF 文件页码与书籍印刷页码；页码无法对应时明确记录。扫描件公式或图注识别不清时，不猜测。
2. **形成候选。** 优先考虑支承条件、载荷路径、整体平衡、几何稳定性、模块连接和接触滑移。为每个候选写出具体触发状态与工程决策，不按教材小节机械拆分。
3. **筛选迁移性。** 将关键结论分为：可直接使用、前提满足时可用、仅作定性启发、当前不适用。淘汰依赖不可获得状态且无法给出有用替代决策的候选。
4. **建立环境映射。** 将书中的构件、载荷、支承和失效形式对应到已核实的任务、积木与工具，列出无法对应的部分。
5. **编写策略。** 把知识变为观察、计算、条件分支、方案选择、候选操作和反馈检查，而不是在代码注释中重写教材。
6. **设计验证。** 分开给出逻辑自测、几何检查、局部物理仿真的验证方案；没有执行记录就写未执行。
7. **整理关系。** 仅在已有技能之间提出有理由的关系，不为凑图而造技能或依赖。

一条技能应解决一个可辨认的决策问题。例如，“识别当前支承假设是否成立”可以独立成技能；“结构力学基础”太宽；“所有桥都加三角形”没有足够适用条件。

## 4. Code as Policies 的具体要求

### 参考策略的边界

默认每条技能包含一个短小、确定性的 Python 参考函数，以显式输入表达当前任务与已知状态，返回可审查的决策或操作建议。它是供 Agent 阅读的知识内容，不是已安装的工具、运行器或自动构建宏。

策略可以计算几何目标、比较满足前提的方案、提出已有 API 的候选操作，或判断需要补充哪些信息。不能只给出“遵循某原则”的自然语言占位函数。

首版参考代码应为无副作用的纯函数，优先使用 Python 标准库。不导入或实例化 `Machine`，不访问文件、网络、数据库或 GUI，不调用模型，不使用 `eval`、`exec`，不安装依赖。

需要构建操作时，返回操作提案，由拥有权限的原角色逐步使用已有工具。每次观察真实返回值后再决定下一步，不把参考函数中的条件分支自动注册成新的执行能力。

### 输入、输出与不确定性

- 对每个输入说明类型、单位、坐标系、来源、是否必需，以及它是实测、任务给定、从文本整理还是推断。参考函数的输入字典只是该技能的约定，不是仓库已有状态 API。
- 原文没有结论、观测缺失、模型假设不成立和观测明确否定，应产生不同的处理；不能用默认零值或乐观猜测补齐状态。
- 验证数值范围、维度、有限性和分母条件。容差与安全余量应有来源，或明确作为待验证的启发参数，不伪装成物理常数。
- 返回至少包含 `status`、`reason`、`checks` 和 `next_steps`。建议状态为 `candidate`、`not_applicable`、`insufficient_evidence`；`candidate` 仅表示可供角色考虑，不表示物理通过。
- `checks` 中每项记录判断依据及结果，未知用 `null`。`next_steps` 可以是补充观察、方案修改或工具提案，不能把没有反例当作完成验证。
- 工具提案须写明 `owner_role`、`tool`、`arguments` 及预期反馈，签名和权限必须有代码依据。这是技能内容格式，不是宣称已实现的执行协议。
- 需要尚未获得的积木 ID、面或位置时，先返回补充观察的建议。不要猜测 ID 自增、操作成功或失败后状态完全不变；不得生成含未解析占位值的可调用参数。
- 若描述多步策略，明确停止条件和有界尝试次数。缺少实体反馈时只输出到下一个观察点，不写无限循环或无条件长操作序列。
- 辅助函数必须完整定义，或引用已审核的技能及版本；禁止把 `compute_optimal_bridge()` 等未实现函数藏在代码里。

如果原理暂时无法在已知信息上可靠编码，标记 `policy_mode: knowledge_only`，保留有效的知识与信息缺口；不要为了“有代码”而编造传感器、物理求解器或空壳算法。

### 逻辑与物理分别验证

参考函数应附最小自测，覆盖正常输入、不适用或边界输入、缺失或非法输入。可以使用普通 `assert`，不引入新测试框架。

自测验证代码分支，不证明公式适用于游戏；几何检查不证明连接强度；一次局部仿真也不证明跨跨度或跨结构泛化。

## 5. 每条技能的输出格式

每条技能使用一个 Markdown 文件，以 YAML 元数据开头，正文保存知识、参考代码与自测。不为每条技能创建包、类层次或单独的执行框架。

以下字段是草案格式，示例中的占位内容须替换为已核实信息；无法确认的值写 `null` 并解释原因。

```yaml
---
id: support_<stable_name>
title: <具体工程决策的名称>
summary: <触发情形、解决的问题及主要限制，供检索使用>
version: 0.1.0
policy_mode: reference_only
applicability:
  categories: [support]
  levels: []
  roles: []
  stages: []
  triggers: []
prerequisites: []
environment_constraints: []
sources:
  - file: <本地原文相对路径>
    title: null
    edition: null
    chapter: null
    pdf_pages: []
    printed_pages: []
    locator: null
    license_status: unconfirmed
    supports: []
code_evidence:
  - path: <相关仓库文件>
    symbol: <函数、类、配置键或任务段落>
    supports: <该处代码实际支持的环境映射或工具约束>
validation:
  human_review: pending
  logic_tests: not_run
  geometry_checks: not_run
  physics_trials: not_run
  evidence: []
---
```

正文按以下小节组织：

1. **何时使用与何时不用**：具体触发状态、作用角色、适用范围及反例。
2. **原理与来源**：用自己的话解释结论；将每条关键结论对应到原文定位。分开标识教材结论、环境事实、作者提出的启发和实测结论。
3. **环境映射与限制**：列出支承、连接、坐标、单位和模型假设，明确哪些条件在 Besiege 中未被验证。
4. **Procedure**：观察什么，如何判断或计算，形成什么方案或操作建议，下一步检查什么；同时给出信息不足和失败分支。
5. **输入约定与参考策略**：逐项说明输入来源，给出完整的 Python 函数；`knowledge_only` 则写清不能编码的原因和所缺信息。
6. **最小自测**：提供可运行的合成输入与断言，标明这些不是实验数据；是否执行按事实填写。
7. **Checklist**：使用前后各列必要检查，区分可由逻辑确认、需工具观察、只能仿真验证的事项。
8. **验证方案与证据**：明确待验证假设、对照条件、可观测量和失败标准；无数据时只写方案，不填预期成功率或最大承载数值。
9. **交给下一角色的结论**：列出需写入计划或蓝图的决定、关键假设和未解风险，不传递整篇原文。Planner 的子结构相关结论须能随 `sub_structures` 进入后续任务。

每条技能应能独立阅读，不依赖另一条技能提供关键安全前提。内容使用中文，代码标识使用 ASCII。表达尽量紧凑，不复制整份任务描述或整本积木目录。

## 6. 技能关系与最终交付

默认输出到 `skill/drafts/`；仅在实际产生草案时创建目录。不要覆盖原书、审核记录或已有同名技能；有冲突时报告并采用明确的新草案文件名。用户要求只返回文本时，不写文件。

最终交付：

- 一份简短的批次说明：实际读取的书籍版本与页码范围、环境依据、候选取舍、已输出文件及未解决问题。
- 每条技能的 Markdown 草案。
- 有可信关系时附 `relations.json`；没有关系时不创建空文件，也不创建悬空边。

关系采用 `requires`、`uses`、`specializes`、`repaired_by`，方向遵循 `skill/PLAN.md`。每条边记录 `source`、`target`、`type`、`reason`、`condition`，并标记 `review_status: pending`。端点必须是本批次或已有的稳定技能 ID；修复关系必须说明观察到何种失败后才成立。

人工审核前不把候选边当作已审定的检索图，也不修改冻结版本或正式实验配置。不根据正式评测结果反复调技能；验证方案先使用开发阶段的场景或参数。

## 7. 提交前自检

- 关键工程结论是否实际来自已读原文，页码与公式是否可定位？未知是否如实保留？
- 每条技能是否回答一个具体决策问题，而不是教材摘要或空泛建议？
- 是否明确区分书籍理想模型、代码环境事实、启发式建议和物理证据？
- 是否遵守接触支承、中央加载、坐标转换、子结构数量和积木可用性？
- 策略是否能产生有依据的方案或下一步，而不仅仅是打印原则？
- 引用的工具是否真实存在、参数正确、当前角色有权限？是否错误地访问了假想的状态字段？
- 是否将信息不足与明确不适用分开，避免默认通过、臆造接触力或材料参数？
- 正常、边界和缺失输入是否有逻辑自测？没有执行的验证是否全部标记未执行？
- 技能正文、代码注释和字符串是否含会触发当前工作流终止条件的保留标记？输出前根据 `spatial/agent.py` 检查并改写，必要检查不应把标记原样带入技能正文。
- 是否保留原角色的输出协议和工具权限，没有把参考策略升级成自动执行宏？

完成后只汇报本次真实产物、资料缺口和待审核事项。不要宣称技能已经提高成功率、经过仿真验证或已接入 Agent，除非有对应的实际记录。
